# 双持方立论 — 交叉对抗调度 skill

收到 `$立论` 时先解析参数，判断是否包含持方。

## 输入解析

```
$立论 <辩题> [持方] [题解] [立论方向] [对抗轮数]
```

- **辩题**（必填）：如「在流量时代下，"酒香不怕巷子深"的经营理念已经过时/仍未过时」
- **持方**（可选）：正方 / 反方
- **题解、立论方向、对抗轮数**（可选）：同【立论】skill

## 规则

1. **无持方参数** → 走本 skill 的**交叉对抗**流程（下一节），最后正反各出一套交付物：
   - 顶层文件夹名保留两个持方表述，用「—」分隔（去掉引号与斜杠）
   - 例：辩题「……已经过时/仍未过时」→ 顶层文件夹「……已经过时—仍未过时」
   - 该文件夹内建「正方」「反方」两个子文件夹，各自存放该持方的 md 与 xlsx（文件名保留持方全称）
   - 例：`……已经过时—仍未过时/正方/……已经过时.md`、`……已经过时—仍未过时/反方/……仍未过时.md`
   - **双持方下不适用【立论】skill 的中性文件夹合并规则**：顶层文件夹始终用「A—B」命名，不改成中性辩题名
   - 最后依次发送两个 PDF（发文件时不附大段说明文字，直接发文件）
2. **有持方参数** → 正常调用【立论】skill（文件夹名只保留我方持方全称，按【立论】skill 原规则）；该 skill 内部已经有两个 agent 互为正反，不需要再套一层交叉对抗

## 核心：交叉对抗（与单持方模式的区别）

单持方模式是「我方一个 agent + 一个专门来打的对手 agent」。双持方模式下**两个 agent 天然就是对方的对手**，所以顺序反过来：

- **正方 agent**：写正方立论；同时**扮反方**去打反方 agent 的草案
- **反方 agent**：写反方立论；同时**扮正方**去打正方 agent 的草案
- **Lead**：锁共同基准、主持两条对抗线、对两方的每条论点各自裁决

也就是说，两方各跑一条完整的对抗线，攻击方都是对面那个 agent，**没有一个是假设出来的对手**。每个 agent 在两个记录里角色相反（正方记录里它是 proposer，反方记录里它是 opponent），这是正常的，不算 fallback。

## 工作流（无持方时）

1. 读取【立论】skill 全文：`~/.dsh/skills/argument-construction/SKILL.md`，以及它指向的 `references/`（诊断 / 证据 / 论证链 / **对抗 / 攻防** / 版块 / excel）
2. **先确认一次交付档位与对抗轮数**（精简 / 标准 / 完整），两个持方共用同一档位与轮数；**论点个数与档位无关**，两方都固定 3 个论点；用户当前消息已指定则跳过
3. **起两个 agent**（优先级：Agent Teams 的 `spawn_teammate` → `subagent` → Lead 分饰两角，兜底必须在两份记录与报告附录里标 `fallback: true`）
   - 两个 agent 必须用**同一模型与同一思考等级**；否则模型差异会被误当成论证差距，两条对抗线的裁决一起失效
   - 每个 agent 在两条对抗线里角色相反（正方记录里正方是主笔，反方记录里反方是主笔），这是设计如此，**不算 fallback**
4. **锁四项**（开打前必须一致）：同一份辩题诊断卡、同一套举证责任分配（只有方向相反）、同一批事实基准、同一档位与轮数
5. **交叉对抗回合制**（轮数按档位，详见 `references/adversarial-debate.md`）：
   - 阶段一 · 诊断对齐：两侧各出诊断卡 → 比对命题类型与论证结构，不一致先修正读法
   - 阶段二 · 草案交换：两侧各出论点草案（`A1/A2/A3` 编号 + 一句话主张，**每方固定 3 个论点**），**互交给对面**
   - 阶段三 · 交叉攻击：第 k 轮，正反两方**同时**用固定攻击字段打对面草案；各自按修补字段回应上一轮收到的攻击
   - 阶段四 · Lead 双裁决：对每方的每条论点判 存活 / 修补后存活 / 降级为次要栏 / 删除，写理由；某方存活论点**少于 3 个** → 该方回炉补料，**不许硬凑**（论点固定 3 个，与档位无关）
   - 阶段五 · 定稿出文件
6. 每方各写一份对抗记录到 `~/.dsh/tmp/<任务名>/`（如 `debate_zheng.json` / `debate_fan.json`），各自跑一次：
   
   `python ~/.dsh/skills/argument-construction/scripts/check_debate.py <debate.json> --md <该方报告.md> --tier <档位>`
   
   硬项通过后再调 `precheck.py <数据.json> --md <报告.md> --tier <档位>`，最后 `generate_report.py xlsx`。md / xlsx 写入共享文件夹下对应的「正方」/「反方」子文件夹（文件名带各自持方全称）；PDF 与所有中间文件留在 `~/.dsh/tmp/`
7. 交付：通过消息工具依次发送两个 PDF，不附加大段说明文字；交付文件夹内只留两方的 md / xlsx（及同名 PDF）

## 双持方特有要求

- **诊断卡互证**：两方的命题类型与论证结构必须一致（同一道题、同一读法），只有举证责任分配相反。若两侧诊断卡不一致，说明至少一方读题有误，先修正再继续。
- **steelman 用真材料**：阶段二的草案交换就是同步点——第 6 节「对方最强版本」必须引用另一方**真实的论点编号与主张**，不许凭空想象；反过来，自己被打的点在对抗记录里必须留原文。
- **编号各自独立**：两方来源编号互不通用（`[1]` 在正方与反方报告里含义不同），不得互相引用来源编号。
- **互为攻防参考**：两侧的交锋点（`F1/F2`）尽量对齐到同一批事实上，便于赛后对照谁的事实更站得住。
- **论点数量一致且固定 3 个**：两方都是 3 个论点（三档一致，档位只加证据密度与对抗轮数，不加论点个数）。一方 3 个、另一方 4 个会让双裁决失去可比性——`check_debate.py` 的 H3b（草案登记）与 H9（裁决后存活）会直接卡住。
- **§4 只写自己**：两方的正文论点体系都不得预判对方反驳（不出现「对方会说……」）；对方视角只出现在第 6、8 节，且**用对方真的说过的话**。
- **对抗记录各写各的**：攻击用对面板的原文，修补写自己实际怎么改的、付了什么代价；不许把对方的让步写成自己的战果。

## 注意

- 正反两方各自独立检索、独立标注证据状态；**不要为了对称而硬凑字数或凑证据条数**
- 交叉对抗中两方都在改动，Lead 要在每轮结束时读双方最新版本再裁决，**不能拿旧版本判分**
- 若持方表述不明确（如「正」/「反」缩写、仅写一方），以用户明确标注为准；仍不确定则停下来询问
- 两侧都要过 `check_debate.py` 与 `precheck.py`；只有一侧通过、另一侧硬项失败时，先修失败的那一侧，不要直接交付一半
